Step 01

Query Understanding

把原始表达整理成轻量语义对象，强调结构化输入，而不是直接在入口里硬编码逻辑。

Step 02

Proposal Engine

当前主路由是 LOCATE，真正已打通的是定位路线，CROP 和 REWRITE 还只是预留。

Step 03

Prompt Bridge

这是 V1 的关键层，把 proposal 转成 segmenter 可稳定消费的 prompt package。

Step 04

Segment + Evaluate

SAM 分割和 LLM evaluator 都已挂上统一 adapter，失败时由 orchestrator 决定是否重试。

Step 05

Artifacts + Report

本地 artifact store 和 demo report 已经能沉淀任务摘要，便于继续做可视化与追踪。

  • 旧版仓库追求“完整产品形态”，包括前端和完整 Web 任务流。
  • 当前主线更重视“新架构 V1 的稳定边界”，先把 contracts、orchestrator、runtime boundary 理顺。

还没有收口的部分

这部分正是为什么我不建议把它称作“已经完工的网页产品”。

产品层缺口

  • 当前主线 API 很薄，离上传、队列、WebSocket、结果下载等完整交互还有距离。
  • 现主线没有接回可直接展示的前端；旧版前端更多是参考资产，不是现在的集成结果。
  • 配置系统还是结构化 dataclass 为主，环境变量/配置文件解析没有完全落地。
换句话说，仓库现在更适合开发者演示和继续研发，不是直接给非技术用户开箱即用。

能力层缺口

  • ProposalRoute.LOCATE 是当前唯一真正实现的路线，CROP / REWRITE 仍是预留接口。
  • 很多真实能力默认仍通过 mock 装配回退，说明“默认可运行”和“默认真实可用”不是一回事。
  • 全量测试虽然都过了，但 4 个 real smoke 仍是 opt-in，默认结果不能代表真实模型环境全绿。
这不算坏事，反而说明项目在控制复杂度；只是它还处在“可进化内核”而不是“稳定成品”的阶段。

结论

先成内核，再成产品

当前节奏是对的。项目最难的“结构清晰且能跑起来”已经做到了，接下来主要是把外层体验和默认真实可用性补完整。
