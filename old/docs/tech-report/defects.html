缺陷 1：工具选择与回退链过长，失败时容易退化成低价值路径

代码证据： pipeline.py 会按 Qwen 输出在 object_locator、concept_generator、 image_enhancer、report_no_mask 之间分派；如果解析不到合法工具，还会落到“未知动作”分支，直接走 SAMProcessor.segment_with_text() 兜底。与此同时， mllm_processor.py 解析失败时默认回退成 concept_generator。

  • 为什么可能导致效果差： 出错时不是一次明确失败，而是可能多次退化到并不适合当前场景的工具，造成“看起来系统还在努力，其实越跑越偏”。
  • 影响范围： 工具选择、失败恢复、结果可解释性。
  • 修复优先级： P1。
  • 是否需要运行验证： 需要。静态上能确认链路复杂，具体多大程度伤害精度要靠样例验证。
  • 对应整改： 跳到 P1：显式化工具回退策略
效果风险 代码可证事实

缺陷 2：定位后端“名义可替换，实际不对称”

代码证据： tools/object_locator.py 里 embedded GridGround 初始化失败后，只有在显式注入非空 train_adapter_client 时才会自动切到 HTTP。默认 pipeline 里只是 ObjectLocator(self.mllm)，所以常见情况是 embedded 不可用时落到 MLLM 网格回退，而不是自动走 TrainAdapter。

  • 为什么可能导致效果差： 定位失败时，回退质量差异很大，但上层看起来都叫“定位工具”，容易误判问题根源。
  • 影响范围： 点提示质量、目标定位一致性、部署行为可预测性。
  • 修复优先级： P1。
  • 是否需要运行验证： 需要。静态上能确认逻辑不对称，具体对精度伤害大小要实跑比较。
  • 对应整改： 跳到 P1：重构定位后端抽象
代码可证事实 维护风险

缺陷 3：pipeline 里有几处状态字段名义存在、实际几乎不演化

代码证据： grid_info 只初始化和传参，没看到对 self.state["grid_info"] 的回写；current_text 只在开始时赋值； results 初始化后基本未被使用。

  • 为什么可能导致效果差： 这类字段本身未必直接损伤精度，但会让人误以为系统有更丰富的状态更新逻辑，增加调参和 debug 时的误判成本。
  • 影响范围： 理解成本、调试路径、后续重构难度。
  • 修复优先级： P0。
  • 是否需要运行验证： 不需要。静态代码已经足够确认其活跃度很低。
  • 对应整改： 跳到 P0：收敛闲置状态
代码可证事实 静态推断

缺陷 4：结果评估策略可能过于保守，且“失败原因”信息压缩得太少

代码证据： 评估阶段只要求 MLLM 给出 Accept/Reject 和被拒序号， 没有结构化的失败原因字段。Reject 时如果没给出索引，还会默认拒绝最新候选。

  • 为什么可能导致效果差： 如果系统只知道“被拒绝了”，却不知道是“目标错了、只分到一半、边界断裂、还是多个目标混在一起”，下一轮工具选择就很难精准纠错。
  • 影响范围： 迭代质量、错误恢复能力、日志可解释性。
  • 修复优先级： P2。
  • 是否需要运行验证： 需要。这里的伤害大小要靠实际失败样例才能量化。
  • 对应整改： 跳到 P2：评估策略重构

缺陷 5：文档、默认值和实现存在轻微漂移

代码证据： Config.EXAMPLES_DIR 默认指向 examples/， 但仓库目录和 README 使用的是 example/；main.py 的 --output_dir help 还是旧路径表述。

  • 为什么可能导致效果差： 它不会直接降低模型精度，但会提高误配置概率，让“环境没配对”伪装成“模型效果差”。
  • 影响范围： 上手成本、部署稳定性、排障效率。
  • 修复优先级： P0。
  • 是否需要运行验证： 不需要。
  • 对应整改： 跳到 P0：统一配置与文档漂移
代码可证事实 协议风险

缺陷 6：前后端双通道同步依赖快照重建，缺少更精细的去重说明

代码证据： 前端在任务运行时同时开 WebSocket 和 6 秒轮询；store 的 hydrateJobStatus() 会在拿到快照时重放整串事件来重建 iterations。

  • 为什么可能导致效果差： 它主要影响“你怎么看到结果”，不是“模型怎么分割”；但如果状态展示不稳，排查真实缺陷会更困难。
  • 影响范围： UI 一致性、调试体验、日志可信度。
  • 修复优先级： P1。
  • 是否需要运行验证： 可选。静态上已能确认机制，是否会造成可见重复事件需浏览器侧验证。
  • 对应整改： 跳到 P1：补前后端事件说明
代码可证事实 建议

缺陷 7：可测试性信号偏弱，仓库里几乎看不到直接的测试入口

代码证据： 根目录没有明显的 tests/、pytest 或单元测试组织痕迹。 当前验证方式更像脚本启动 + 人工观察结果。

  • 为什么可能导致效果差： 一旦开始修算法和状态流，没有回归测试很难知道是“真的变好”还是“只是换了一种坏法”。
  • 影响范围： 修改信心、回归验证、长期维护。
  • 修复优先级： P1。
  • 是否需要运行验证： 不需要确认其缺失，但后续补测试本身需要执行验证。
  • 对应整改： 跳到 P1：让后续重构可回归验证

缺陷 8：用户看到的是结果和轮次，但不容易理解“为什么系统这么选”

代码证据： 前端会展示工具名、分数、判定和日志，但缺少更结构化的“本轮选择原因”“失败原因摘要”“下一轮改了什么”的解释层。

  • 为什么可能导致效果差： 不会直接影响模型输出，但会严重影响你定位缺陷的速度，尤其是在模型策略错误时。
  • 影响范围： 演示效果、开发体验、问题定位效率。
  • 修复优先级： P1。
  • 是否需要运行验证： 可选。静态上已能判断缺解释层，具体是否足够影响使用可后续演示验证。
  • 对应整改： 跳到 P1：补说明层和协议说明
