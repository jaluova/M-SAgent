先看懂项目，再谈修改

仓库本身是在做“文本指代图像分割”，核心链路是 Qwen2.5-VL 决策工具、GridGround/TrainAdapter 定位、SAM3 产出 mask，然后再让 MLLM 对结果做二次验收。现在效果“一言难尽”，很大概率不只是模型本身弱，而是整条工具链的策略、回退、状态和评估联动存在问题。

这份站点解决什么

把架构说明白，把静态可见的问题挖出来，把后续整改路线排优先级。

这份站点不做什么

不伪装成实验报告，不把静态推断当成已验证事实，也不直接重写核心模型逻辑。

核心结论摘要

你现在可以先记住这 6 件事

事实

这是一个“入口多样、核心管线共享”的仓库。CLI 和 Web 最终都落到 MLLMSAMPipeline。

事实

真正决定每轮走哪条路的，不是固定流程，而是 Qwen 通过 prompt 选择 object_locator / concept_generator / image_enhancer。

静态推断

“效果差”不太像单点问题，更像多处策略耦合导致的系统性退化：选错工具、回退路径低价值、评估逻辑保守或混乱，都会拖垮最终结果。

风险

embedded GridGround 和 HTTP TrainAdapter 虽然都叫“定位后端”，但默认回退并不对称，这会让定位失败时的行为难以预测。

风险

pipeline 内部有几处“名义上很重要、实际上几乎不更新”的状态字段，会增加阅读成本，也可能掩盖真实控制流。

建议

第一阶段不要急着大改模型。先把配置漂移、闲置状态、日志、回退说明和协议描述收拢，能显著提升后续调参与排障效率。

资料来源

这份报告用了哪些材料

1. 仓库源码与配置

重点来自 pipeline.py、 mllm_processor.py、 tools/object_locator.py、 server/job_manager.py、 frontend/src/stores/job-store.ts。

2. README 与现有比赛报告

README 给了运行方式和模块分区；根目录的比赛作品报告主要提供背景叙事、术语、原始目标和一些理想化设计表述，但本站不会沿用它的比赛写法。

3. 5 个 gpt-5.4 explorer agents

我们把仓库分成入口、核心推理、工具链、后端服务、前端状态 5 个切面并行只读勘探，用来减少人工漏读和误读。

4. 静态搜索到的问题线索

包括大量 fallback、错误打印、未见测试入口、文档与实现轻微漂移、以及若干状态字段疑似闲置等。
