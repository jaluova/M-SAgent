优先级总览

先别急着碰模型，把台面收干净

从静态分析看，最合理的顺序不是一上来猛调 prompt 或阈值，而是先把 “文档和实现漂移、闲置状态、回退边界、日志和协议说明”收拢。因为只有系统行为先变得可理解，后面的效果优化才不会变成盲猜。

图 5. 整改优先级图。
P0

高信心、低风险、立刻能改善可维护性的问题

统一配置与文档漂移

清理 example/examples、旧 output_dir 描述、默认值说明，让启动失败不再伪装成模型效果差。

收敛闲置状态

梳理并删除或注释解释几乎不演化的字段，降低阅读与调试噪音。

增强日志可解释性

让工具选择、回退、评估拒绝时输出更清楚的原因摘要，而不只是“失败/Reject”。

补接口与运行说明

把前后端协议、结果文件和事件流写成开发文档，降低误解系统行为的成本。

P0 为什么要先做

这些问题不一定直接提高 cIoU，但会显著减少误配置、误判和“我不知道现在系统到底在干嘛”的状态。 你后面想改定位、评估或 prompt，都会更有把握。

P1

需要代码重构，但静态上已经能判断值得改的部分

重构定位后端抽象

把 embedded GridGround、HTTP TrainAdapter、MLLM fallback 明确成等价的 provider 边界，别再让默认回退逻辑藏在初始化细节里。

显式化工具回退策略

把“解析失败”“工具失败”“评估拒绝”这几类失败分开处理，避免多层 fallback 叠在一起。

收拢 pipeline 状态模型

只保留真正参与控制流的状态，把视觉上下文、候选集和工具历史建成更明确的结构。

补前后端事件说明

让 WS 与轮询的职责边界更清楚，必要时增加去重或版本号机制。

P1 预期收益

P1 的核心价值不是“立刻涨点”，而是让系统行为变得稳定、可理解、可比较。没有这一层，P2 的效果优化会很难判断到底是模型变好了，还是只是换了条回退路径。

P2

必须结合实跑验证的效果优化项

工具选择 prompt 调优

检查 Qwen 到底在什么图像和查询上选错了工具，再改 system prompt 与用户提示构造。

评估策略重构

给评估阶段加入更结构化的失败原因，而不是只给 Accept/Reject。

裁剪增强策略

验证 image_enhancer 的网格框、放大尺度、截断拒绝规则是否过于保守或不稳定。

定位阈值与动态 top-k

比较 embedded 与 HTTP 路径在点质量上的差异，重新审视阈值配置和点扩展策略。

P2 的前提

这里已经超出静态分析能力边界了。真正做 P2 时，必须配套失败样例、可复现实验记录、修改前后对比和最小回归测试。

执行顺序

如果明天开始改，建议按这个顺序推进

  1. 先做 P0：清理文档漂移、闲置状态、日志和接口说明。
  2. 再做 P1：把定位后端和回退链路从“隐式行为”改成“显式结构”。
  3. 等系统行为更可解释后，再做 P2 的实跑优化。
  4. 在每个阶段结束时补一份“小规模回归样例集”，哪怕只有人工挑选的十几张图。
