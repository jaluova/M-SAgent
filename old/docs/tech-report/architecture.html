总体图

先建立一个整体心智模型

这个仓库不是一个“单模型直出结果”的项目，而是一个多工具协作的推理系统。你可以把它理解成： Qwen 负责想办法，SAM3 负责真正画 mask，定位模块负责帮它找到空间线索，Web 和前端只是把这条链路包装成任务系统。

两条主链路

CLI 和 Web 并不是两套不同系统

图 3. CLI 与 Web 调用链对照。
CLI 链路

启动器通常是 scripts/run_single_gpu_stable.sh， 它先检查 Python、SAM3、显存和配置，再执行 main.py。 main() 解析 --image、--text、--max_iter 等参数后，直接实例化 MLLMSAMPipeline 并调用 run()。

Web 链路

Web 入口是 server/app.py 被 uvicorn server.app:app 启动。FastAPI 在生命周期里创建 JobManager，后者接收上传任务、放进队列，然后照样调用 MLLMSAMPipeline.run()。

组件职责

每个模块到底负责什么

MLLMProcessor

加载 Qwen2.5-VL，负责“这一轮该调用哪个工具”和“当前 mask 能不能接受”两类决策。

SAMProcessor

负责真正的分割执行，支持文本提示分割和点提示分割，是最终 mask 的直接来源。

ObjectLocator

负责把文本查询变成空间点位，来源可以是 embedded GridGround、HTTP TrainAdapter，或者 MLLM 的网格回退提示。

ConceptGenerator

当原始 query 太模糊时，它会尝试多组概念改写，再逐个交给 SAM 做文本提示分割。

ImageEnhancer

当目标太小、太远、太密时，它会先裁剪并放大局部，再交给 SAM 分割并把 mask 还原回原图。

JobManager + 前端

负责任务排队、事件分发、结果标准化和 UI 消费，不直接参与模型推理决策。

多轮推理

为什么这个项目要一轮一轮地跑

核心原因是作者不信任“一次分割就一定对”。所以 pipeline 不是“输入文本就直接出 mask”，而是每轮先分析，再执行，再生成检查图，再让 MLLM 二次评估。如果这一轮被判成 Reject，系统不会立刻认输，而是保留仍有价值的候选， 换一种工具或提示继续跑。

这一点很关键： 项目效果差，不一定是某个模型单独不行，也可能是“工具选错了、评估太保守、回退路径太差”导致的系统级问题。
状态流

系统内部主要记住哪些状态

在 pipeline 内部，真正跨轮演化的核心状态是： iteration、accepted_masks、current_image、 final_image 和 tool_history。它们分别表示当前轮次、已经保留下来的候选 mask、 下一轮给 MLLM 看的上下文图、当前最像“最终答案”的可视化图、以及前几轮尝试过什么。

另外还有一些“看上去很重要、但静态阅读里几乎不演化”的字段，比如 grid_info、current_text、results。这些字段会增加读代码时的心理负担， 因为你会下意识觉得它们承担了很多职责，但实际上在当前实现里并不活跃。

Web 端的状态则被拆成三层：原始事件 events、按轮聚合的 iterations、以及最终结果 result。这是一种比直接把所有事情都塞进一个 store 更清晰的做法。

资源生命周期

模型和资源是怎么被持有的

Qwen 的生命周期

MLLMProcessor 初始化时加载 Qwen2.5-VL，并构造 SharedQwenBackbone，供 embedded GridGround 复用视觉/文本编码能力。

SAM3 的生命周期

SAMProcessor 也是对象级持有，但推理时会临时上 GPU、结束后回 CPU。 这说明仓库在主动做显存折中，而不是把所有模型都一直钉在 GPU 上。

Web 任务资源

JobManager 会缓存 pipeline 和 SAM 实例，避免每个任务都从头重建。 代价是后端目前更像“单进程、单队列、共享模型对象”的服务。
